# GamingShorts V3 — full-game production

V3 extends the installed runtime, its existing editorial SQLite database and its
durable production queue. It does not introduce a second renderer, speech bridge,
publication system or automatic game switch. No full recording, AI analysis or
speech was started during implementation.

## Import and start

Place the complete original Cairn recording in **`D:\GamingShorts\GameSources\cairn\`**.
For example, use `cairn-full.mp4`. Copy with a `.partial` extension, rename after
completion, and let it settle for at least 60 seconds. This folder is deliberately
outside the legacy watcher's `Sources/` inbox. Do not put the new full recording
in that inbox. No preliminary five-minute user test is required.

Run these commands in Ubuntu/WSL, substituting the actual filename:

```bash
cd /mnt/d/GamingShorts
python3 start.py --v3 register --game cairn --title Cairn --source "/mnt/d/GamingShorts/GameSources/cairn/cairn-full.mp4"
python3 start.py --v3 select --game cairn
python3 start.py --v3 estimate
python3 start.py --v3 index --start
```

Registration performs strict FFprobe packet/container checks and a streaming
SHA256. It neither selects the game nor calls AI. `select` explicitly authorizes
the active game. `index --start` authorizes full decoding, proxy construction and
Codex visual analysis. Only timestamped contact sheets and bounded scene context
are supplied to Codex; the original recording is never uploaded to it.

Keep the legacy `--watch` worker stopped while using explicit V3 batches. V3 uses
the same locks and queue; two competing workers are refused. The legacy watcher
is paused during activation to keep expensive processing inactive. It can still
be started explicitly for the legacy workflow with `python3 start.py --watch`.

## Inspect and produce three Shorts

```bash
python3 start.py --v3 games
python3 start.py --v3 inventory --limit 100
python3 start.py --v3 history --limit 100
python3 start.py --v3 batch --count 3 --start
```

The batch command prints its ID and plans up to three distinct Shorts. It calls
Codex for concepts, narratives and independent visual-evidence review; it does
**not** call speech or enqueue rendering. Each accepted plan reserves its footage
atomically, including its scene signatures. If insufficient diverse unused scenes
remain, planning stops for attention rather than reusing footage or fabricating
a new event. A partially completed batch and its plans remain available.

Use the printed ID in the next command to authorize speech and rendering:

```bash
python3 start.py --v3 run --batch BATCH_ID --start
python3 start.py --v3 batch-status --batch BATCH_ID
python3 start.py --queue
```

Only the selected batch's jobs are claimed through the existing worker. Broken
recordings/render attempts become `needs_attention`; other valid batch items can
continue. The existing free-only Garret handoff, uncertain-call safeguards,
waveform-safe cuts, float audio mix, real word timestamps, karaoke, licensed music,
original-source rendering and technical QC remain in use. Final delivery retains
native cadence up to the configured 60 FPS cap. Selected moving original footage
also receives cached cadence QC before speech: a 60 FPS container with only
15 visual updates/second is refused; genuinely static scenes are exempt.
Length follows the story within
the existing configurable 25–40-second range, rather than a fixed 20 seconds.

Watch/listen before using the existing `--project "PATH" --approve` command.
Approval binds to exact output bytes. Publication remains an explicit manual step.
No spoiler warning card is added. Spoiler-free footage screening is a separate
editorial policy: uncertain or major-spoiler scenes are excluded.

## Recovery

```bash
# Reuse completed validation windows, proxies, analysis and indexed chunks:
python3 start.py --v3 index --start --retry

# Only after inspecting a failed/uncertain AI analysis attempt, explicitly permit a new analysis call:
python3 start.py --v3 index --start --retry --retry-ai

# Resume planning an interrupted batch; completed plans remain intact:
python3 start.py --v3 batch --start --retry BATCH_ID
python3 start.py --v3 batch --start --retry BATCH_ID --retry-ai

# Resume production after inspecting the individual project and logs:
python3 start.py --v3 run --batch BATCH_ID --start --retry

# Persistently reject an indexed moment:
python3 start.py --v3 reject-scene --scene SCENE_ID --reason "Uninteresting or spoiler-containing"

# Abandon a stopped/planned batch while retaining every asset and reservation:
python3 start.py --v3 close-batch --batch BATCH_ID --reason "No more worthwhile unused material"
```

`--retry-ai` archives the prior analysis attempt before another Codex call. It
never sets `--retry-voice` or `--new-voice`. A saved successful speech result is
reused; an uncertain speech attempt stops for existing voice-handoff recovery.
A source modified since registration is refused, preserving the original catalog
and history. A changed path/recording is never silently rebound to a game.

For another game, create `GameSources/GAME_ID/`, register it with a new game ID,
then explicitly select it. Exhaustion never switches games automatically.

## Architecture and checkpoints

| Component | Extension |
| --- | --- |
| `game_store.py` | Additive `game_*` tables in `Database/editorial_v2.sqlite3`: game/source, scenes, batches, shots, exclusions and reservations |
| `game_index.py` | Complete overlapping chunk timeline, strict checkpointed decoding, proxy/contact-sheet artifacts, cached AI receipts, scene-change hints and visual signatures |
| `game_plan.py` | Unused-scene ranking, dense inspection, three concept alternatives, narrative/evidence review, durable shot reservations and targeted queue dispatch |
| `full_game.py`, existing `start.py` | Explicit `--v3` commands, source namespace guard, no automatic production or game changes |
| Existing `job_store.py` | Strict decode checkpoints in `automation.sqlite3`, targeted atomic claim, unchanged queue/retry compatibility |
| Existing `source_validation.py` | Streaming FFprobe/FFmpeg checks, size/duration-aware deadlines, bounded progress buffer, strict window completion and stall detection |
| Existing `common.py` | Scoped reuse of a verified original's checksum; narration, code and other asset hashes remain fresh |
| Existing `editorial.py` | V3 dispatch and evidence/source/diversity guard before speech/render, bounded preview decoder threads |

The catalog is additive: existing V2 rows and schemas are retained. Existing
`edits` rows remain canonical for hooks, topic/premise, narrative structure,
rejection feedback, approval and publication status. `game_shots` adds game/source
identity, exact original-relative shot intervals and visual signatures. Earlier
V2 reservations on the same source are also respected. Cairn bridge exclusions
combine conservative semantic tags with retained historical bridge exemplars
where available. Neither timestamp overlap nor alternate narration makes footage
eligible again. Rejected/closed work retains its reservations.

Analysis artifacts live under
`FootageIndex/sha256_<SOURCE_HASH>/FullGame_<INDEX_KEY>/chunk_00000/`.
Each chunk has a small proxy, absolute-timestamp contact sheets, artifact checksums,
scene-change hints and isolated AI request/result receipts. Source, settings,
index code, FFmpeg binary, AI adapter and font changes invalidate the index key.
Old indexes are retained. An interrupted chunk can reuse its validated artifacts;
completed chunks are not decoded or sent to AI again. Failed/uncertain AI calls
require explicit retry authorization.

## 60 GB / seven-hour resources

There is no 32-bit size limit or full-recording RAM allocation. Checksums stream
1 MiB blocks, FFprobe returns summary metadata, FFmpeg streams pixels and compressed
media, and scene/candidate metadata is bounded. H.264, HEVC and AV1 are supported
when installed FFmpeg can decode them. Registration currently requires one video
stream, a known FPS and at least 1920×1080 original resolution.

Defaults are 120-second analysis chunks with six-second overlap, a 640-pixel-wide
2 FPS H.264 proxy, CRF 30 and a 384 kbit/s maximum video rate. Seven hours produces
221 chunks and roughly 884 contact sheets. The nominal capped proxy allowance is
about 1.27 GB; the estimator budgets approximately 1.91 GB including margin,
0.23 GB for contact sheets, 0.81 GB for three render workspaces and 2 GiB free-space
reserve: approximately **5.1 GB additional free space**, excluding the original
60 GB file, existing data and accumulated future exports. These are planning
budgets, not hard quotas. Free space is checked before validation/indexing, before
each chunk and before V3 rendering. Writes can still fail if another application
consumes the disk concurrently; state remains resumable and originals are untouched.

Strict decode uses overlapping 600-second validation windows. Only completed,
unchanged-source windows get receipts. A full successful coverage receipt is
shared with the existing worker so rendering does not decode the full source
again. Source checksums are also reused only under the exact registered filesystem
fingerprint and verified integrity receipt. Changed metadata stops production.
The one-time packet scan and initial checksum remain necessary full-file reads;
they are not checkpointed. Validation and proxy creation normally decode the
source in two passes, trading some CPU time for independently reusable integrity
receipts and simple recovery. No full-resolution intermediate copy is created.

The default per-window deadline allows 32 times that window's real-time length;
the stall watchdog separately allows 180 seconds without advancing frame/time
progress. Legacy full-decode deadlines now scale with recording duration too,
instead of rejecting a progressing seven-hour source after two hours. FFmpeg
progress is printed every 30 seconds during long decoding. Use shell log redirection
or `tee` to retain the command's progress output.

Indexing is serial under the existing workflow lock. Decoder, filtering and proxy
encoder thread pools are bounded (default two each); this is not a whole-process
RAM or CPU quota. Decoder memory still depends on codec, resolution and reference
frames. Several GiB of available RAM is prudent; an actual peak-RAM benchmark on
the new recording remains outstanding. The proxy pass and full validation represent
roughly 14 hours of source-time decoding plus overlap. At an observed effective
0.5× / 1× / 2× decode speed, that work alone would take approximately 28 / 14 / 7
hours, plus AI latency and disk I/O. These are arithmetic scenarios, not measured
machine performance or a completion-time promise.

Expect about 221 initial chunk-analysis calls and up to nine planning/review calls
for a successful three-story batch, with bounded dense-preview work. Codex account
usage depends on image processing, context and retries; no fixed price is assumed.
Speech remains free-model-only. Completed artifacts/results are reused across
future Shorts. No such full-recording or production calls were made for verification.

## Configuration

Optional settings in the existing `config.json` under `full_game`:

```json
{
  "full_game": {
    "chunk_seconds": 120,
    "overlap_seconds": 6,
    "proxy_width": 640,
    "proxy_fps": 2,
    "proxy_crf": 30,
    "proxy_maxrate_kbps": 384,
    "validation_chunk_seconds": 600,
    "validation_realtime_factor": 32,
    "stall_seconds": 180,
    "threads": 2,
    "reserve_free_gib": 2
  }
}
```

Merge this object into the current configuration; preserve its voice and render
settings. Changes to analysis policy create a new index version, retaining the old
one. Increasing sampling increases CPU, storage and AI image coverage/cost.

## Verification and remaining limits

Verification uses isolated synthetic fixtures and no AI services. The complete
suite covers seven-hour timeline coverage, overlap/global timestamps, 64-bit
60 GB metadata, source identity, historical reservations, visual repetition,
atomic reservations, interrupted indexing/validation/batch planning, explicit
spend gates, receipt/cache reuse and invalidation, scoped source hashes and the
existing corruption, cadence, audio, captions and queue regressions.
Actual FFmpeg fixtures exercise strict decode, checkpoint reuse, a late source
window, timestamped sheets, scene signatures, proxy reuse, truncated-range
rejection and unchanged original bytes. The existing full render smoke test
checks positive narration/motion QC and rejects a music-only negative case.
The full suite passes **160 tests**. The installed V3 handoff also passes a real
25-second render through source guards, durable reservations and shared strict
integrity receipts, including a music-only negative test. Exact logs, preserved
database backups and release checksums accompany the versioned release.

The seven-hour recording is not available yet: no real 60 GB throughput, peak RAM,
AI editorial accuracy or final three-story batch is claimed. Still-frame sampling
cannot guarantee identification of every brief worthwhile moment. Sparse evidence
is conservatively rejected; full timeline coverage is not exhaustive understanding.
Visual hashes are heuristic and can miss alternate views or over-reject similar
rock faces; AI spoiler/evidence review can also be wrong. Human watch/listen and
explicit approval remain necessary. The current shortlist inspects up to 12 ranked
unused scenes per story; a rejected plan stops for inspection rather than blindly
trying more AI calls. Rendering quality remains governed by the existing tested
cadence, crop, audio and caption pipeline; technical QC does not prove narrative
quality or perceptual cleanliness.
